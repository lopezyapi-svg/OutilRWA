================================================================================
INTRODUCTION GENERALE AUX DIAGRAMMES
================================================================================

Ce document regroupe sept (7) diagrammes UML 2.5 produits dans le cadre de la
conception de l'OutilRWA, application de calcul des actifs ponderes par le
risque (RWA - Risk-Weighted Assets) selon le referentiel prudentiel BCEAO /
Bale II. Ces diagrammes forment ensemble la documentation architecturale
complete du systeme, chacun eclairant un aspect different : structure des
donnees, architecture logicielle, cas d'utilisation, flux de traitement,
interactions entre composants, organisation interne des agregats metier et
structure du code source.

Les sept diagrammes se completent selon la logique suivante :

  3.6.1 Diagramme de classes    -> Quoi est stocke (modele de donnees)
  3.6.2 Diagramme de composants -> Comment le systeme est organise (architecture)
  3.6.3 Cas d'utilisation       -> Qui fait quoi (fonctionnalites utilisateur)
  3.6.4 Diagramme d'activite    -> Comment le calcul RWA est execute (algorithme)
  3.6.5 Diagramme de sequence   -> Dans quel ordre les composants dialoguent
  3.6.6 Structure composite     -> Comment une fiche exposition est reconstruite
  3.6.7 Diagramme de paquetage  -> Comment le code source est organise

Tous les noms de tables et colonnes sont en francais, conformement au schema
SQL de la base de donnees locale (SQLite, fichier rwa_data.db).


================================================================================
3.6.1 - DIAGRAMME DE CLASSES
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme de classes est le diagramme central de la conception. Il represente
la structure statique de la base de donnees relationnelle de l'application, en
montrant les 29 tables, leurs attributs et les relations entre elles. Il est
construit selon la methode MERISE (Methode d'Etude et de Realisation Informatique
pour les Systemes d'Entreprise) normalisee en 3NF (troisieme forme normale), ce
qui garantit l'absence de redondance et l'integrite des donnees.

ORGANISATION DES TABLES (6 groupes - 35 tables au total)
----------------------------------------------------------
1. ENTITES CENTRALES (2 tables) :
   - contreparties : enregistre chaque entite economique (banque, entreprise,
     Etat, organisme public, etc.) avec sa categorie prudentielle et sa notation.
   - expositions : enregistre chaque credit ou engagement bilan accorde a une
     contrepartie, avec le montant brut, la devise, les resultats de calcul
     (EAD, RWA, capital) et le discriminant de type prudentiel.

2. SOUS-TABLES DE SPECIALISATION MERISE (12 tables) :
   Chaque exposition appartient a exactement un (1) des 12 types prudentiels
   definis par le referentiel BCEAO. Pour eviter une table unique avec 30+
   colonnes dont la plupart seraient NULL, le modele applique la specialisation
   MERISE : une sous-table par type, liee par cle primaire/etrangere partagee
   (exposition_id = FK vers expositions.id).
   Le champ type_prudentiel dans expositions joue le role de DISCRIMINANT : il
   indique quelle unique sous-table est active pour cette exposition, ce qui
   interdit toute ambiguite et toute double appartenance.
     a) exposition_souveraine       : Etats et banques centrales
     b) exposition_organisme_public : Organismes publics et collectivites
     c) exposition_bmd              : Banques multilaterales de developpement
     d) exposition_banque           : Etablissements de credit
     e) exposition_entreprise       : Entreprises du secteur prive
     f) exposition_clientele_detail : Petites creances (< seuil reglementaire)
     g) exposition_immo_residentiel : Prets immobiliers residentiel occupant
     h) exposition_immo_commercial  : Financements immobilier commercial
     i) exposition_souffrance       : Creances en situation de defaut
     j) exposition_risque_eleve     : Placements a risque eleve (150% fixe)
     k) exposition_autre_actif      : Autres actifs (cash, immobilisations, etc.)
     l) exposition_hors_bilan_detail: Engagements hors bilan (via CCF)

3. TABLES CRM (3 tables) :
   CRM signifie Credit Risk Mitigation (attenuation du risque de credit).
   - crm_financee    : collateral financier (depot, titre, OPCVM) avec calcul
     des decotes reglementaires He, Hc, Hfx et du ratio EVA/CVA.
   - crm_non_financee: garantie personnelle d'un tiers (banque, Etat) avec la
     ponderation du garant substituee a celle de l'emprunteur.
   - crm_garanties   : table de garanties multiples permettant des scenarios
     de couverture partielle ou de paniers de garants.

4. REFERENTIELS REGLEMENTAIRES (4 tables) :
   Ces tables sont pre-chargees avec les valeurs du referentiel BCEAO et ne
   changent pas pendant l'utilisation courante.
   - baremes_ponderation      : correspondance segment x notation -> ponderation (%)
   - baremes_ccf              : facteurs de conversion credit par type d'engagement
   - references_notation      : nomenclature officielle des echelons de notation
   - references_pays_souverains: notation souveraine et ponderation par pays

5. REPORTING, AUDIT ET SYSTEME (7 tables) :
   - rapports / lignes_rapport   : historique des rapports Excel/PDF generes
   - engagements_hors_bilan      : module dedie aux engagements hors bilan
   - historique_imports          : traçabilite de chaque import CSV/Excel
   - journal_operations          : journal de toutes les operations (CREATE,
     UPDATE, DELETE) pour l'audit
   - schema_migrations           : versionnement du schema de la base de donnees
   - metadonnees_app             : parametres et metadonnees de l'application

6. MODULE RISQUE OPERATIONNEL (7 tables) :
   Module de gestion du risque operationnel (Basel II - Pilier 1 & 2).
   - ro_incidents      : incidents et evenements de perte operationnelle
   - ro_kri_definitions: definition des indicateurs cles de risque (KRI)
   - ro_kri_valeurs    : valeurs mesurees des KRI dans le temps
   - ro_risques        : cartographie des risques (probabilite x impact)
   - ro_controles      : resultats des controles de conformite
   - ro_plans_action   : plans d'action corrective ou preventive
   - ro_historique     : journal d'audit du module risque operationnel

POINT CLE : LE DISCRIMINANT MERISE
------------------------------------
Le champ type_prudentiel (valeurs a..l) dans la table expositions est le
point architectural le plus important du modele. Sans lui, rien n'empecherait
une exposition d'avoir simultanement une ligne dans exposition_souveraine ET
dans exposition_entreprise, ce qui serait une incoh'erence metier grave. Avec
ce discriminant, le code applicatif garantit qu'une seule sous-table est
alimentee par exposition, et le diagramme le documente explicitement avec le
stereotype <<discriminant>>.

================================================================================
3.6.2 - DIAGRAMME DE COMPOSANTS
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme de composants decrit l'architecture physique et logicielle du
systeme, c'est-a-dire comment les grandes parties du logiciel sont organisees,
quelles sont leurs responsabilites et comment elles communiquent entre elles.
Il repond a la question : "Comment le systeme est-il construit ?".

L'OutilRWA suit une architecture client-serveur locale a 4 couches, chaque
couche ayant une responsabilite unique (principe de separation des
responsabilites) :

COUCHE 1 - FRONTEND FLUTTER (Windows Desktop)
----------------------------------------------
C'est l'interface graphique que voit et utilise l'analyste prudentiel.
Developpe avec le framework Flutter pour Windows, il communique exclusivement
avec le backend via des requetes HTTP/JSON. Il ne contient aucune logique
de calcul : son seul role est d'afficher les donnees et de transmettre
les actions de l'utilisateur. Il est compose de 8 ecrans specialises
(Expositions, CRM, Hors Bilan, Analyse, Dashboard, Capital Planning,
Referentiels, Rapports) et d'un service HTTP centralise (RwaApiService)
qui encapsule tous les appels API.

COUCHE 2 - ROUTES FASTAPI (Backend localhost:8000)
---------------------------------------------------
C'est la porte d'entree du backend. Les routes (RouterExpositions,
RouterCRM, etc.) recoivent les requetes HTTP, valident les donnees
d'entree via Pydantic (typage strict, plages de valeurs, champs requis)
et deleguent le traitement aux services metier. Elles ne contiennent
aucune logique metier propre.

COUCHE 3 - SERVICES METIER ET CALCUL PRUDENTIEL
------------------------------------------------
C'est le coeur fonctionnel de l'application. Les services orchestrent
les operations : ils appellent le moteur de calcul RWA (RwaCalculationService,
~1536 lignes implementant les formules BCEAO/Bale II) pour determiner
EAD, ponderation et RWA, puis font appel aux repositories pour la
persistance. Cette couche contient aussi les validateurs d'import
(Excel, CSV) qui verifient la conformite des fichiers avant integration.

COUCHE 4 - REPOSITORIES ET BASE SQLITE
---------------------------------------
Les repositories (ExposureRepository, CrmRepository, etc.) sont les seuls
composants autorises a interagir avec la base de donnees. Ils executent
les requetes SQL (SELECT avec JOIN, INSERT OR REPLACE, DELETE) et
retournent des objets Python structures. La base SQLite locale (fichier
rwa_data.db) stocke toutes les donnees de maniere persistante, sans
necessite de connexion reseau externe, ce qui garantit la disponibilite
de l'outil meme hors connexion.

POURQUOI CETTE ARCHITECTURE ?
------------------------------
Cette separation en 4 couches permet de modifier l'interface graphique
(ex: remplacer Flutter par une application web) sans toucher au calcul
prudentiel, ou de changer la base de donnees (ex: migrer vers PostgreSQL)
sans toucher aux services metier. Chaque couche est independante et
testable separement.

================================================================================
3.6.4 - DIAGRAMME D'ACTIVITE
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme d'activite modelise le flux de traitement d'une exposition depuis
sa reception jusqu'a sa persistance en base, en passant par toutes les etapes
de validation et de calcul prudentiel. Il repond a la question : "Comment le
calcul RWA est-il execute, etape par etape ?". C'est la traduction algorithmique
du referentiel BCEAO (Banque Centrale des Etats de l'Afrique de l'Ouest) /
Bale II en diagramme de flux.

ETAPE 1 - RECEPTION ET IDENTIFICATION (entree)
-----------------------------------------------
Les donnees d'une exposition arrivent soit par saisie manuelle de l'analyste
via l'interface Flutter, soit par import d'un fichier Excel/CSV. La premiere
action est d'identifier parmi les 12 categories prudentielles (a a l) a quelle
categorie appartient cette exposition, car la ponderation de risque et les
parametres de calcul different selon la categorie.

ETAPE 2 - VALIDATION EN PARALLELE (fork)
-----------------------------------------
Deux verifications sont effectuees simultanement (representees par le fork) :
- Verification de la zone reglementaire (UEMOA ou CEMAC) qui peut modifier
  certaines ponderation (exemple : creances libellees en FCFA sur des emetteurs
  UEMOA peuvent beneficier de ponderation preferentielles).
- Validation Pydantic des champs obligatoires : types de donnees, plages de
  valeurs acceptables, presence des champs requis selon la categorie.
Si la validation echoue, l'enregistrement est rejete et tracabilise dans les
tables historique_imports et journal_operations, puis le traitement s'arrete.

ETAPE 3 - CALCUL DE L'EAD (Exposure At Default)
-------------------------------------------------
L'EAD represente le montant d'exposition au moment du defaut. Pour les
expositions au bilan, l'EAD = montant brut. Pour les engagements hors bilan,
l'EAD = montant nominal * CCF (Credit Conversion Factor), le CCF etant lu dans
la table baremes_ccf selon le type d'engagement.

ETAPE 4 - APPLICATION DE LA CRM (Credit Risk Mitigation)
----------------------------------------------------------
Si une garantie eligible est associee a l'exposition, deux cas se presentent :

a) CRM financee (collateral financier : depot bancaire, titre d'Etat, OPCVM) :
   On calcule les decotes reglementaires :
   - He : decote sur l'exposition (0% pour les credits au bilan)
   - Hc : decote sur le collateral selon son type (0% a 30%)
   - Hfx : decote supplementaire si devise du collateral differente (8%)
   Puis : EVA = EAD * (1 + He)  et  CVA = Valeur_collateral * (1 - Hc - Hfx)
   L'EAD net = max(0, EVA - CVA), soit l'exposition non couverte residuelle.

b) CRM non financee (garantie personnelle d'un tiers : Etat, banque, institution) :
   La portion garantie beneficie de la ponderation du garant (substituee a
   celle de l'emprunteur). Le RWA total est la somme de la portion garantie
   (EAD * taux_couverture * ponderation_garant) et de la portion non garantie
   (EAD * (1-taux_couverture) * ponderation_emprunteur).

ETAPE 5 - DETERMINATION DE LA PONDERATION
-------------------------------------------
Selon la categorie prudentielle et la notation de la contrepartie, la
ponderation applicable est determinee en consultant la table baremes_ponderation.
Les ponderation varient de 0% (creances sur Etats OCDE bien notes) a 250%
(etablissements bancaires sous procedure prudentielle). La note laterale du
diagramme resume les regles de ponderation pour chacune des 12 categories.

ETAPE 6 - CALCUL FINAL ET PERSISTANCE
----------------------------------------
RWA = EAD_net * ponderation (en fraction, ex: 0.75 pour 75%)
Capital_minimum = RWA * 8% (ratio de solvabilite minimum Bale II)
Ces resultats sont persistes dans les tables expositions, la sous-table du
type prudentiel correspondant, et eventuellement crm_financee ou
crm_non_financee. Le tableau de bord est ensuite mis a jour.

3.6.5 - DIAGRAMME DE SEQUENCE
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme de sequence modelise les interactions chronologiques entre les
differents composants du systeme pour realiser une operation specifique. Il
repond a la question : "Dans quel ordre les composants dialoguent-ils et que
s'echangent-ils ?". A la difference du diagramme d'activite qui montre le flux
algorithmique, le diagramme de sequence montre qui appelle qui, avec quels
parametres et dans quel ordre.

L'operation choisie pour l'illustration est l'import d'un fichier Excel
d'expositions, car c'est l'operation la plus complexe du systeme : elle
implique 8 composants differents, une validation en 2 temps, une transaction
SQL et plusieurs etapes de persistance enchainees.

PROTOCOLE DE VALIDATION EN 2 TEMPS
------------------------------------
L'import suit deliberement un protocole en deux phases pour eviter les imports
partiels silencieux (situation ou une partie des lignes est inseree et une
autre rejetee sans que l'utilisateur s'en rende compte).

Phase 1 - INSPECTION (confirm=false) :
L'analyste selectionne le fichier. Le backend recoit le fichier, l'analyse
(colonnes detectees, apercu des 5 premieres lignes, mapping sugere) mais ne
persiste rien en base. Il retourne uniquement un rapport d'inspection que
l'interface affiche pour que l'analyste puisse verifier le mapping des colonnes.
Cette phase est sans effet de bord : elle peut etre relancee autant de fois
que necessaire.

Phase 2 - IMPORT REEL (confirm=true) :
Apres confirmation de l'analyste, le backend effectue la validation complete
ligne par ligne. Si des erreurs sont detectees (valeur hors plage, type
incorrect, colonne manquante), le traitement s'arrete et retourne la liste
des erreurs par ligne (code HTTP 422) sans inserer quoi que ce soit en base.
Si toutes les lignes sont valides, l'import est execute dans une transaction
SQL atomique : toutes les insertions reussissent ensemble, ou aucune n'est
executee (garantie ACID).

SEQUENCE D'INSERTION DANS LA TRANSACTION
------------------------------------------
L'ordre des insertions est contraint par les cles etrangeres :
1. INSERT OR REPLACE INTO contreparties (doit exister avant les expositions)
2. INSERT OR REPLACE INTO expositions (reference contreparties.id)
3. INSERT INTO exposition_<type_prudentiel> (reference expositions.id)
4. INSERT OR REPLACE INTO crm_financee ou crm_non_financee (reference expositions.id)
5. COMMIT (valide l'ensemble de la transaction)
6. INSERT INTO historique_imports (traçabilite de l'operation d'import)

La notation "OR REPLACE" permet de gerer a la fois l'insertion de nouvelles
expositions et la mise a jour d'expositions existantes (upsert), identifiees
par leur cle primaire.

PARTICIPANTS ET RESPONSABILITES
---------------------------------
- EcranExpositions (Flutter) : interface utilisateur, ne contient aucune logique
- RwaApiService    : client HTTP centralise du frontend, serialise/deserialise JSON
- RouterExpositions: point d'entree FastAPI, valide les types via Pydantic
- ExcelImportValidator : extrait et valide le contenu du fichier Excel
- ServiceExpositions   : orchestre l'import, cree les objets metier
- ExposureRepository   : execute les requetes SQL sur la table expositions
- CrmRepository        : execute les requetes SQL sur les tables CRM
- SQLite rwa_data.db   : base de donnees locale, garantit la persistance

3.6.6 - DIAGRAMME DE STRUCTURE COMPOSITE
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme de structure composite modelise la structure interne d'un
composant complexe, en montrant ses sous-parties et leurs interconnexions.
Ici, il decrit comment l'agregat metier "ExpositionComplete" est reconstruit
par le repository a partir de la base de donnees. Il repond a la question :
"De quelles parties est constituee une fiche exposition complete, et comment
ces parties s'assemblent-elles ?".

NOTION D'AGREGAT METIER
------------------------
Dans l'application, le frontend recoit toujours une fiche exposition complete
(ExpositionComplete), jamais des donnees partielles en plusieurs requetes.
Cette fiche unique est le resultat de la fusion de 13 tables differentes
en une seule requete SQL utilisant des LEFT JOIN. C'est le repository
(ExposureRepository) qui est responsable de cette reconstruction, via la
methode _row_to_record() qui transforme la ligne SQL fusionnee en objet
Python structure (ExposureView), serialise ensuite en JSON vers le frontend.

AVANTAGE : le frontend fait 1 seule requete HTTP pour obtenir toutes les
informations d'une exposition (donnees de base + contrepartie + details du
type prudentiel + CRM), ce qui simplifie considerablement le code Flutter
et evite les problemes de synchronisation entre requetes paralleles.

DESCRIPTION DES 4 BLOCS
-------------------------
BLOC 1 - BASE (table : expositions)
  Contient les donnees fondamentales de l'exposition : identifiant, reference
  a la contrepartie, type prudentiel (discriminant), montant brut, devise,
  statut (Active/Soldee/Contentieux), mode CRM, et les resultats de calcul
  (EAD, RWA, capital, ponderation initiale et finale). Ce bloc est toujours
  present, quel que soit le type d'exposition.

BLOC 2 - CONTREPARTIE (table : contreparties)
  Contient les informations sur l'entite emprunteuse : nom, categorie
  prudentielle officielle, notation externe et notation du pays de domicile.
  Ces donnees sont jointes via contrepartie_id (INNER JOIN obligatoire car
  une exposition sans contrepartie n'a pas de sens).

BLOC 3 - DETAILS DE TYPE [1 parmi 12] (sous-tables de specialisation)
  C'est le bloc le plus important pour la comprehension du modele MERISE.
  Exactement UNE des 12 sous-tables est presente par exposition, determinee
  par le discriminant type_prudentiel. Les 11 autres sous-tables renvoient
  NULL sur les colonnes concernees (LEFT JOIN). Par exemple :
  - Pour type_prudentiel = 'a' : seul le bloc exposition_souveraine est
    renseigne (cas_particulier, ponderation_zero_preferentiel, oce_etabli, oce_note)
  - Pour type_prudentiel = 'e' : seul exposition_entreprise est renseigne
    (depasse_seuil_degradation_bceao, procedure_prudentielle, sfi_hors_loi_bancaire)
  Cela permet au frontend de n'afficher que les champs pertinents selon le
  type, sans logique conditionnelle complexe cote serveur.

BLOC 4 - DETAILS CRM [0..1] (tables crm_financee et crm_non_financee)
  Ce bloc est optionnel : il n'est present que si l'exposition est associee
  a une garantie (crm_existe = 1). Selon le mode de garantie (crm_mode) :
  - crm_financee  : contient les parametres du collateral (type, valeur,
    devise, decotes He/Hc/Hfx, EVA, CVA, EAD apres CRM, gain CRM)
  - crm_non_financee : contient les informations du garant (nom, categorie,
    notation, ponderation, taux de couverture)
  Les deux sous-blocs sont mutuellement exclusifs pour une exposition donnee.

CONNEXIONS ENTRE BLOCS (LEFT JOIN)
------------------------------------
Les fleches entre blocs representent les jointures SQL :
  - BASE -> CP   : contrepartie_id = contreparties.id  (INNER JOIN)
  - BASE -> TYPE : exposition_id = <sous-table>.exposition_id (12 LEFT JOIN)
  - BASE -> CRM  : exposition_id = crm_financee.exposition_id (2 LEFT JOIN)
La requete SQL complete comprend donc 1 + 12 + 2 = 15 jointures simultanees,
ce qui illustre la puissance du modele relationnel pour reconstruire des
agregats complexes en une seule operation.

================================================================================
3.6.7 - DIAGRAMME DE PAQUETAGE
================================================================================

DESCRIPTION ET ROLE
-------------------
Le diagramme de paquetage (Package Diagram) represente l'organisation physique
du code source en modules, packages et fichiers. Il repond a la question :
"Comment le code source est-il structure, et quelles sont les dependances entre
les differentes parties du projet ?". C'est la vue la plus proche de
l'arborescence de fichiers reelle du projet.

Ce diagramme est utile pour comprendre la maintenance et l'evolutivite du
systeme : en voyant les dependances, on peut identifier quels composants sont
isoles (faciles a remplacer) et lesquels sont tres couples (a modifier avec
precaution).

PACKAGE BACKEND
---------------
Le backend est organise en deux grands sous-packages :

app/ (logique applicative)
  Ce package contient tout ce qui concerne la logique metier et l'API REST,
  independamment de la base de donnees. Il est subdivise par domaine
  fonctionnel (expositions, hors_bilan, crm, referentiels, rapports, dashboard),
  chaque domaine ayant ses propres routes (endpoints FastAPI), services
  (logique metier) et modeles Pydantic (schemas de validation et serialisation).
  Le sous-package core contient la configuration globale, les fonctions de
  calcul partages et la gestion des chemins de fichiers au runtime.
  Le sous-package validators contient les logiques de validation et
  transformation des fichiers d'import (Excel, CSV).

database/ (persistance et calcul)
  Ce package contient tout ce qui touche a la base de donnees et au calcul
  prudentiel intensif. Il est egalement subdivise :
  - repositories/ : un fichier par domaine de persistance, chacun encapsulant
    les requetes SQL du domaine correspondant. Les repositories ne connaissent
    pas les services et les services ne connaissent pas SQL.
  - services/ : le moteur de calcul RWA (rwa_calculation_service, ~1536 lignes
    implementant les formules BCEAO), le service d'import Excel et le service
    d'export PDF/Excel.
  - migrations/ : 22 fichiers SQL numerotes (001 a 022) appliques
    sequentiellement par connection.py a chaque demarrage. Ce systeme de
    migrations versionnees garantit que toute base existante est mise a niveau
    automatiquement, sans perte de donnees.
  - connection.py : gestionnaire de connexion SQLite, gestion des migrations,
    des transactions ACID et de la compatibilite runtime.
  - schema.sql : definition du schema de base (28 tables) en SQL, completee
    par les migrations (migration 022 ajoute 7 tables risque operationnel),
    pour un total de 35 tables sur les nouvelles installations.

PACKAGE FRONTEND
----------------
Le frontend Flutter est organise selon la meme logique de separation :
  - core/ : service HTTP centralise (rwa_api_service), configuration,
    modeles de donnees partages et localisation.
  - modules/ : un dossier par ecran applicatif (8 ecrans). Chaque module
    est autonome et communique uniquement via le rwa_api_service.
  - shared/ : composants visuels reutilises entre modules (shell de navigation,
    sidebar, theme graphique).

DEPENDANCES CLES
-----------------
Les fleches pointillees montrent les dependances de compilation ou d'appel :
  - Les routes appellent les services, jamais l'inverse
  - Les services appellent les repositories et le moteur de calcul
  - Les repositories appellent uniquement connection.py (acces SQL)
  - connection.py initialise le schema.sql et applique les migrations
  - Le frontend ne connait que le rwa_api_service (pas les repositories)
Cette structure en oignon garantit qu'aucune couche ne depend d'une couche
superieure, ce qui rend le systeme testable et evolutif.

SYSTEME DE MIGRATIONS VERSIONNEES (001 a 022)
----------------------------------------------
Chaque fichier de migration est un script SQL numerote. Au demarrage de
l'application, connection.py verifie la table schema_migrations pour savoir
quelles migrations ont deja ete appliquees, et n'execute que les nouvelles.
Ce mecanisme permet de deployer des mises a jour de schema (ajout de colonnes,
renommage de tables, creation de nouvelles tables) sur des bases existantes
sans recreer la base depuis zero ni perdre les donnees des utilisateurs.
La migration 021 (021_renommage_francais.sql) renomme toutes les tables et
colonnes de l'anglais vers le francais. La migration 022 (022_risque_operationnel.sql)
ajoute les 7 tables du module de gestion du risque operationnel.
